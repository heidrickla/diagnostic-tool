# Diagnostic Tool design

## Shape

The tool exists to fix other people's PCs. A technician, who may work with an AI model, diagnoses and repairs; the checks are the survey that comes first, so the bigger problems stand out and the whole system is in view before any work starts.

One portable Windows x86-64 executable, `DiagnosticTool.exe`, with no installer, no service, no startup entry and no listening port. The C runtime is linked in and imports resolve from System32 only, so the file runs from a Downloads folder on a stock Windows 10 or 11 PC. It runs as the current user; the checks and the toolkit never ask for elevation. Data recovery and changing crash dump settings are the exceptions: the drive window's Recovery button starts a second copy of the program through Windows' administrator prompt (`--recovery --disk N`), which skips the start screen and the checks, holds its own single-instance mutex beside the normal window, shows only the recovery window and ends when it closes; the crash dump window's Change settings as administrator does the same with `--crash-dumps --record <file>`, showing only the crash dump window and adding its changes to the starting window's change record.

The user's path is: double-click, read one start screen, choose Start, keep working. The user authorizes the work by asking the technician for help and choosing Start; nothing else asks the user to approve anything, and Windows' own administrator prompt is the only other thing the user may see. The technician and the AI model decide each repair, and every command and change goes in the activity record. The window and the report are written for the technician and the AI model.

## Data recovery

The recovery tools read a drive someone handed over because it is failing, so every one keeps the same rules, stated at the top of `src/recovery/mod.rs`. The source (a disk, an image file or an unlocked volume) is opened for reading only, and shared. Every write goes to one of three places: a new output folder on another disk, checked through handles (`recovery::dest`) before anything is read; the replacement drive the technician picks in Write image to a replacement drive; or the differencing copy Repair on a copy makes over an image. One module, `crate::handles`, owns every handle that can change a disk or volume: it alone names a disk by its number, opens a disk or volume with a write right, and sends a lock, dismount, extend, layout, attribute or ATA command. Each of its types (`HeldDisk`, `DiskWriter`, `CopyDisk`, `AtaDisk`, `SctDrive`) opens once, proves the handle is the drive meant through that handle, and holds it until the act ends; an act takes the type, never a number, letter or path. A source test scans all of `src/` for these and fails if one appears elsewhere. A failed read is recorded and skipped, never retried automatically, and recorded only while the drive is shown to answer (below); failed areas are read again only in bounded passes the technician, or an agent the technician directs, starts (Fill the gaps). Work that can hang on a failing drive runs under `recovery::timed`, and long work stops and resumes. Every output file is entered in the ledger when made and ends whole, damaged, partial or removed. Unknown is never taken as fine: on a path that changes something (a write, a registry value, an unlock or relock, a drive's read limit, an attach, a repair, a crash dump setting), a result that failed or could not be read refuses the change or stops it, and on a path that reports something it is said as not known, with its reason, never shown as zero, empty, none or Ready. An ignored error (`let _ =`, `.ok()`, `unwrap_or_default()`, `unwrap_or(..)`, `Err(_) =>`, a poll that drops a closed channel) is allowed only where the failure is already said elsewhere or changes nothing; a value dropped with no one left to tell (in `Drop`) is recorded in the session's change record (`handles::record_unseen`). Source tests check the patterns that can be checked mechanically: the disk paths (`handles` tests), the crash dump, key and BitLocker paths (`restore` tests), the parsers' reads (`budget` tests), and the windows' result polls and the image attach (`recovery` tests). A blocking call on a path that changes something (the drive's read limit set and put back, every BitLocker call through WMI, a virtual disk made, attached or detached, a volume locked and dismounted, the replacement drive taken offline and brought online) runs within a time limit through `recovery::timed::owned`, and what undoes it travels with the call: when the call ends after its caller gave up, at its limit or on Stop, its outcome is handed to that undo on the call's own thread, which puts the change back (a late unlock is locked again, a late attach detached, a late copy removed, a late lock let go so Windows mounts the volume again, a disk that went offline late brought online, the drive's own read limit set once the drive answers the command before it) or records it in the session's change record and says it. A call that may hold an image open (making a copy over it, attaching, detaching) also carries the image's footer: the footer stays due until the last such call has ended, and the one that ends after its caller gave up takes it off as Windows lets the image go, so a late detach leaves the image exactly as it was. Every change job is counted from the moment it starts until the call and its whole undo have ended (`timed::DUTIES`), a late attach and its detach included, and so is every holder of a change undone later: an image's footer, a volume this program unlocked (its `Relock` made on the unlock's own thread), a drive's read limit (from before the set is sent) and a disk taken offline (on the offline job's own thread), so nothing is uncounted between a job and its holder. Each job states its limits (`timed::Job`): how long its caller waits, counted from when its call begins rather than from when it was journalled, the longest Windows is waited for at the process's end (240 s for the virtual disk service, past the 180 s a first detach was measured to be held; chosen bounds of two to four times the limit for the others) and how long its undo takes. A recovery process whose last window has closed waits for every counted job and holder, each as long as it stated, never a fixed time, in a small window saying what it is putting back; a job that would start once that wait is over does not start. What Windows has still not answered by then is entered in the change record. Every job and holder is also entered in a journal, `%ProgramData%\DiagnosticTool\recovery-pending.json`, with the process's id and start time, and removed when it has ended; the next recovery window settles the entries of a process that is gone, ended or killed, as it starts (`recovery::pending`). It changes only what it proves is still exactly what the ended run wrote: this tool's own footer, compared byte for byte and cut off on one handle that shares reading only, and a drive's own read limit, on the drive of that model and serial number while it holds the run's value. Everything else is said and never acted on, since nothing proves it is still the run's: a copy left behind, named with its path and size for the technician to delete, a volume left unlocked, a disk left offline. What is said is only what was read then: a journalled disk number is the number the disk had then, with its model and serial number, never the disk now, and nothing is asked of a disk by its number; a place that could not be read is said as unread, never as empty; a job not seen to end is not said to have failed. Each outcome goes in the change record and in a dialog before the window opens. A source guard (`pending::tests::settling_changes_only_what_it_proves`) holds settling to those two changes. Nothing a late call changed is forgotten. A call that changes nothing may drop a late answer (`timed::in_time`), and a BitLocker listing waits a bounded time for each volume. A source guard (`timed::tests::every_blocking_change_call_is_bounded_and_owns_its_undo`) checks these calls. A BitLocker recovery key stays in memory only, in a zeroing type, and is never shown whole, logged, written to a file or put in an event or result. Saved passwords are not extracted.

Each tool is an engine with no window in it: one entry function taking a typed, serde options struct with documented bounds, a progress callback with typed events, a cancel flag, and a typed, serde result. A confirmation the window asks a person for (a replacement drive's serial number, a recovery key) is a field of the options, checked by the engine, so an agent the technician directs can drive every tool with what the technician tells it. The windows only build the options, show the events and render the result; no decision, guard or limit lives only in a window.

Every parser of untrusted on-disk or firmware data (the NTFS, FAT and exFAT scans, the volume search, the registry reader, the walk of people's folders, the thumbnail cache, the preview search, the file check and its folder listing, Find files by type, the dump folder listing and the SMBIOS table) runs within one budget type, `budget::Budget`. Each states its limits as a `budget::Limits` constant with its numbers and why (items of its own unit, bytes read, memory held, nesting depth, and a time limit unless a person watches it with a Stop button), takes `&mut Budget` at its entry (one parse owns it and its helpers borrow it in turn, so every charge is visible where it is made; only the stop flag is shared), charges it where it reads, keeps or recurses, and stops when a charge is refused. Reaching a limit is never silent: the result names it in words a technician reads (`Budget::said`, for example "The scan of the file table stopped at its limit of 8,388,608 file table records."), and what was found before then is still listed. Depth is the one limit that does not stop a parse: a part nested too deep is left out, counted and said, and the rest goes on; in the file check it makes the file not checked instead. A source guard (`budget::tests`) checks that each parser states its limits and takes the budget. Memory is charged before it is allocated: a buffer or list whose size comes from the data is made only through the budget (`Budget::buffer`, `filled`, `room`, `grow`), which charges it first and gives it back only once the charge is accepted, so a forged size is refused before anything is allocated. What a read makes stays charged while it is held and is freed when it is let go or handed on as part of what is kept; reads of a stream go a piece of at most 1 MiB at a time, so a long run is never held twice over. The sources the thumbnail walk and the preview search read from fill a buffer the walk or search made within its budget, and the file check's read window, the copies it keeps and what it unpacks are charged before they grow. A source guard (`budget::tests::every_sized_allocation_of_a_parser_is_charged_first`) fails on a size-driven `vec!`, `with_capacity` or `resize` in a parser file; the one exception is a list no larger than one already held within the budget (a flag per dump file listed), named with its reason in the guard. A value that could not be read (a length, a time, a folder entry, a file system's first sector, a Wi-Fi profile, the Users folder, a product key record) is said to be unread with why, never taken for empty, zero or 1970.

The recovery window lists the tools in the order a technician uses them: Rescue image and Rescue copy of files (for a drive), Open an image as a drive, Unlock a BitLocker drive (for a drive), Copy the customer's files, Recover deleted or lost files, Find files by type, Check recovered files, and Write image to a replacement drive.

## Deleted and lost files

Recover deleted or lost files and Find files by type read a disk or a rescue image through `recovery::reader::Reader`, which reads in chunks of up to 1 MiB, tries a failed chunk once more in 4 KiB pieces, remembers every piece that failed and never asks the drive for it again; those bytes come back as zeros and are reported. A drive that stops answering ends the reading at once.

Volumes come from the MBR (with its extended chain) and GPT tables, from a search for NTFS, FAT and exFAT boot sectors every 1 MiB and in the sector before (where NTFS keeps its backup boot sector), or from every sector; a found boot sector counts only when the file table or allocation table it points to is there. NTFS is read through $MFT's own runs (record 0 from $MFTMirr if the first copy cannot be read) with update-sequence fixups, records' times, names (the Win32 one first), resident and non-resident data, extension records and attribute lists; paths are rebuilt through parent references, a parent deleted or reused shows as such, and a deleted file's clusters are checked against $Bitmap for intact, partly overwritten or overwritten. A scan reads no more file table records than the volume can hold or 2^23, and holds no more than 2 GiB, counted from the size of each entry and attribute with its name, values and runs, each path, each file listed and the cluster bitmap; past either it stops, says so in the report and lists what it found. A deleted file's clusters are counted against the bitmap by ranges (a running count every 4,096 clusters), never one cluster at a time. FAT12/16/32 folders are walked for files in use and 0xE5 entries with their long names (a deleted long name is kept when its checksum fits some first letter); a deleted file's clusters are taken as contiguous and checked against the table. exFAT entry sets with the in-use bit clear are read the same way, exact for NoFatChain files, following a deleted file's chain only while none of it is in use again. Runs that point outside the volume are never read; their bytes are written as zeros and the file is marked damaged.

The carver reads the whole source in 4 MiB chunks and looks at each sector's start for JPEG, PNG, GIF, BMP, PDF, ZIP (named docx, xlsx, pptx, odt, ods, odp or epub from its entries), MP4 and MOV, RIFF (AVI, WAV, WebP), SQLite, 7z and RAR headers. Each find's end comes from its structure: JPEG markers to EOI, PNG chunks to IEND, GIF blocks to the trailer, size fields for BMP, RIFF and SQLite (page size times page count), the ZIP end record whose central directory sits before it, top-level ISO boxes, 7z's start header and RAR blocks to the end block, and for PDF the last %%EOF before another file's header; each type has a size cap, and a start whose end lies past it is skipped and counted per type (`carve::Carving`). The search carries on after each file. It reads at most three times the source plus the largest cap (`carve::bytes_for`), each find charged as far as its measure looked, so starts forged in every sector end the search at that limit, said, instead of reading the source once per sector.

Recovered files go to a folder that `check_destination` accepts (never the source's disk; output beside an image file is allowed, since new files cannot overwrite an image in use), in their folders or grouped by kind, with names Windows accepts and never overwriting anything ("name (2).ext"). Unreadable parts are written as zeros, and `Recovery report.txt` in the destination lists each file, its state and the byte ranges written as zeros. The test images and how they are made are in `tests/fixtures/recovery/README.md`.

A rescue image is read with the GNU ddrescue map beside it (`x.map` for `x.img`, as the rescue image tool names it, or `x.img.map`), parsed by the rescue image's own parser: every area the map does not mark rescued ('+') reads as a failed read, narrowed sector by sector since an image costs nothing to read again, so a file over one is recovered with zeros there and marked damaged, as from the drive itself. A map fits an image of its size, one a fixed VHD's 512-byte footer longer (the footer is not the drive's and is not read), or one GNU ddrescue left short of an unrescued end. A missing, unreadable or other-size map leaves a plain image, and its description, shown in the window and the report's Source line, says its unread areas are unknown.

A picture recovered with parts missing (by extension: JPEG, PNG, HEIC, GIF, BMP, WebP, TIFF and the raw formats) keeps its zeros, is renamed by its handle to "name (partial).ext" so it sorts beside the original, and the report's "Pictures with missing parts" section gives how much is missing, where, and how far from its start it is whole. Its built-in preview is read back from the file just written, never from the source again, and only from parts that were read (`recovery::preview`): the EXIF thumbnail (IFD1), Multi-Picture previews, a TIFF-based raw file's preview IFDs and SubIFDs (CR2, NEF, ARW, DNG, ORF, RW2, PEF), Fujifilm RAF's header preview and Canon CR3's PRVW and THMB boxes; MakerNote previews are not read. A preview is taken only when it is a whole baseline or progressive JPEG with every segment in bounds and an end marker; the largest is written as "name (preview).jpg" and entered in the ledger. The search of each picture runs within `preview::LIMITS` (16,384 parts, four whole previews' worth read, 4 MiB held, boxes four deep, 30 seconds). The same is an engine on its own (`preview::run`) for pictures recovered earlier.

Save Explorer thumbnails, beside the volume searches, reads Windows Explorer's `thumbcache_*.db` files (formats 20, 21 and 30 to 32: Vista, 7, and 8 to 11) from the volume shown, deleted ones included, through the file system readers (`recovery::thumbcache`). Each entry's JPEG, PNG or BMP is written to `Thumbnails <date>\<cache> (<user>)\<hash>.<type>` when its structure is whole, or as "<hash> (partial)" with zeros where the cache could not be read; an entry that makes no sense is skipped to the next "CMMM" signature. `Thumbnail report.txt` gives each cache's counts and every file from the ledger.

A deleted file's state comes from evidence. Its own volume's allocation map gives intact, partly overwritten or overwritten. On a lost volume, a current partition over its area makes it "at risk" when its start still matches its type, or "may be overwritten" when the type has no fixed start. Assessment makes one read of a file through its runs, at most its first 4 KiB, and never its end, since the source may be failing; an ISO's one read is instead its 2 KiB first volume descriptor at 32 KiB. That read is made once with no retry in pieces (`Reader::read_once`), and a start that cannot be read leaves the file "not judged: its start could not be read". Only a type with a fixed marker at a fixed offset (byte 0, or an ISO's at 32 KiB + 1) whose marker does not match (`carve::Expect`, which accepts every documented variant) makes it overwritten. A PDF without "%PDF-" in its first 1 KiB, or an Office or OpenDocument file without a zip record's signature in its first 4 KiB, may be overwritten, since a valid one may have a longer lead. Zip, jar and sqlite files are not judged by their start. Every state stays recoverable.

## Recovery output

Every output (image, map, copied or recovered file, report, log) is made by `recovery::dest::Guard`. The chosen folder is opened once, checked through its handle (no link, a folder, not on the source disk) and held without delete sharing for the whole run. Each file and folder below it is created with NtCreateFile relative to an already checked folder handle, one name at a time, never following a reparse point, and is checked through its own handle before anything is written; something made and then refused is deleted through its handle. An output is found again by its file ID through OpenFileById, or, on a file system without IDs (FAT, exFAT), by a walk from the held base that checks each step and the file's size and creation time; a file whose identity cannot be confirmed is reported incomplete. The map is written to a scratch file and renamed by handle.

`recovery::ledger::Ledger` enters each output when it is made and gives it a final state: whole, whole with zeroed ranges, partial (stopped or failed after N of M bytes) or removed. A file whose records on the volume are damaged carries that flaw from the reader to its entry (`Item::flaw` from `Found::damaged`, `copy::Tree::damaged` for a rescue copy or Copy the customer's files through the NTFS reader), and is reported damaged, never read in full, however much of it was read. An NTFS file whose runs hold less than its size keeps that size, the rest written as zeros and listed; only a size larger than the volume is cut to what the runs hold. Reports, logs and window notices are built from it alone. Every output file is made by one writer, `recovery::writer`: it makes the file through the destination guard relative to a held folder, enters it in a ledger before a byte is written, counts the bytes it writes through `ledger::write_counted`, and ends the entry whole, partial or removed. A source test fails if any other recovery file or window makes or opens a file for writing (`dest` creation calls, `File::create`, `fs::write`, an `OpenOptions` write or append, a `BufWriter` over a file); the one allowance is the footer `vdisk.rs` puts on the technician's own image to attach it and takes off again. Three files are made by the writer without an entry of their own, each because something finer says what it holds: a rescue image, whose map records every byte; the map, saved whole to a scratch file and renamed over the last good one; and a rescue copy's log, which is the ledger's own output. A report is rendered from the ledger first, then entered in it as it is made (`writer::write_report_file`, tag `REPORT_TAG`, never counted as a recovered file) and ends whole or partial at the bytes written: the Recovery report, the Thumbnail report and the File check report. A report that is a run's only output, the Customer files report and the Write report, is written with a ledger of its own (`writer::write_lone_report`), and its result says how it ended. The rescue copy's log is its ledger: each file's row (path, size, condition, source) is written to the log the moment its state is final, and memory holds only counts and open entries. A file waiting for the second pass stays an open entry, its zeroed ranges the parts to read again, beside its file ID or walk key; its row is written when the second pass ends it. The copy leaves nothing in the destination but the files it made and the log. A report or log is complete only if it ends with "End of report." or "End of log.", written with no line break after it; the header names that line without its full stop, so no cut leaves a document ending with it. The summary comes after the table or the last row, the last line is written only if no write to the document failed, checked after the summary, and a failed write leaves no summary and no last line and is shown in the window. A rescue copy keeps each row whose write failed (up to 10,000) and tries it once more after the log's "incomplete" line, under its own heading; the window gives the count of files made that the log does not list.

A rescue image's map names its source's model, serial and size in comment lines, and where they are known its sector size and the drive's own model and serial number from IDENTIFY (`device::ata_identity`, read on a read-write handle proven to be the held disk, IDENTIFY only). What Windows reports is a USB adapter's while the drive is in its enclosure and the drive's own on a SATA port; the drive's own stays the same. The map also names the part of the drive read, the whole disk or a volume at the byte offset of its extent, and the whole drive's size; where both name a part, another part is another source, and a map that names none needs the technician's yes for a volume. When the map and the drive both carry the drive's own serial number and the part, that and the size decide (`image::match_drive`): equal resumes across the move, another serial is another drive, and another size or sector size is refused and said. When either lacks it, the reported model, serial and size decide as before. The image is looked for under the name the drive's description gives, and when none is there, under a map in the folder naming the drive's own serial number and the same part (more than one is refused, naming them). That search finds the image, rules it out, or says it could not tell: more than 256 maps with images, or a map that cannot be read, is not text, or whose heading runs past its first 16 KiB, is refused with the folder named, and no new image is started. Write image reads each candidate's own identity the same way, in the list and again on the held drive before the refusals, and refuses the source by it; a USB candidate of the source drive's size whose identity cannot be read is refused (at any size for a volume's map without the drive's size), while a drive that carries no ATA command (NVMe) is not. Resuming refuses another drive, an image shorter than the map's last rescued byte, or one not the drive's size, and asks before using a map that names no drive or a drive without a serial number. The image is flushed before every map save, so a saved map never claims bytes the image file does not hold. Opening a source and reading a drive's health run on their own threads with a 30-second limit, so a stalled drive leaves the window and Stop working. End texts come from whether this run saved a map.

## Rescue image: photos first, quick give-up and Fill the gaps

The aim, for a drive that reads some files and times out on others, is to recover as many photos intact as possible, and several tries give the best chance of recovering the data. Photos first, quick give-up and Fill the gaps serve that, within the rule that failed areas are read again only in bounded passes a person or a directed agent starts.

Photos first (`recovery::photos`, `image::Settings::photos_first`, on in the window by default) runs at the start of copying pass 1, and again when a stopped pass 1 resumes. The partition tables and each volume's records (NTFS's MFT, FAT and exFAT tables and folders) are read through the rescue itself (`image::Tap`), so every record read goes into the image and the map as it is made, and an area already rescued is read back from the image instead of the drive. Files ending in jpg, jpeg, jpe, heic, heif, png, gif, tif, tiff, cr2, cr3, nef, arw, dng, orf, raf, rw2, mp4 or mov are listed, deleted ones included, except a deleted file whose start was read and is not its type, or whose space its volume gives to another file; a file whose record no longer says where its content is (seen live: JPEGs deleted on a Windows 11 NTFS volume showed no runs in their records; why is not established) is left out and counted in a note. Their areas are then read in disk order with pass 1's cluster size, a failed read marked non-trimmed (bad when it was one sector) and skipped past with pass 1's growing skip; pass 1 then carries on from its own position. A record read through the rescue that touches a sector already bad is answered as unreadable without reading the drive.

The retry rule inside one run: copying, trimming and scraping read only sectors never tried on their own. Trimming reads the untried edges of a failed area sector by sector and scraping its middle, each sector once; a failed read of one sector marks it bad ('-'), and nothing but a retry pass reads a bad sector again. The retry passes are the ones chosen before Start (`Settings::retries`, "Retry passes" in the window, 0 to 3, default 1): retry 1 is the reverse pass, each bad area read once more from its far end (ddrescue's backwards retry, since some drives read past damage from the other side), and retries 2 and 3 read each bad sector once more forwards. With 0, a run ends after scraping and no failed sector is read again; Fill the gaps is then the way to try again. The map stays a plain GNU ddrescue map: the phase is copying pass 1 throughout and the statuses are ddrescue's. No file system, records that cannot be read, no photos, or records taking longer than `records_limit_secs` (900 s) leave the usual order, said in the window ("Photos first: not used, ..."). The window shows "Photos first: N files, X GB" and the bytes of their areas read and unreadable; `Progress::photos` holds the same figures as `PhotosStatus`.

Quick give-up (`recovery::read_limit`, `tools::drives::sct`) sets an ATA drive's SCT Error Recovery Control read timer: 1.5 s for copying, trimming and scraping, 10 s for the reverse pass, the retries and Fill the gaps, and the drive's own value back at the end of every run, on Stop and when the run's limit is dropped. The command is SMART WRITE LOG of one sector to the SCT command log (action code 3, function 2 to read, 1 to set, selection 1, the read timer), sent by `handles::SctDrive` alone through the disk's ATA transport (below). Its read-write handle is opened once per run, on the first command, and the bus, the model and serial number and IDENTIFY are read on that handle and checked against the drive the source was opened on (`ReadLimit::for_source`); a drive that is not it, or reports no serial number to tell it apart, is sent nothing. Every command goes through the held handle one at a time, each under a 15-second limit, so a drive that leaves and another that takes its number is never sent anything. A set that gets no answer in time may still take effect: nothing more is set, and the drive's own value is still sent back at the end on the same handle, after the command before it. The drive's own value is put back only if the drive still holds the value this run set: the current value is read first, and a drive that holds another (something else changed it) or cannot be read is left as it is and the run says so. A set refused after an earlier one took effect keeps the handle, so the earlier one is still put back. An NVMe drive or a drive on another bus, or one whose IDENTIFY word 206 lacks SCT error recovery control, is sent nothing; a drive or USB adapter that refuses it is read as it is, and the window says it will take its own time on each bad sector. The setting is volatile: a power cycle resets it.

ATA commands (`tools::drives::ata`, `tools::drives::sat`, `handles::AtaDisk`) are one register-level `ata::Command` (features, count, LBA low, mid and high, device, command, direction, one 512-byte sector) that can be built only as SMART READ DATA, SMART READ THRESHOLDS, IDENTIFY DEVICE or the SCT read limit, and one `AtaDisk::execute` that sends it through the carrier the bus read on its own handle calls for. On an ATA, SATA or RAID bus that is Windows' ATA paths: SMART_RCV_DRIVE_DATA for the reads and IOCTL_ATA_PASS_THROUGH for the SCT command. On USB it is SCSI/ATA Translation: ATA PASS-THROUGH (16) or (12) in an IOCTL_SCSI_PASS_THROUGH (`sat::exchange`): the form last proven on the handle goes first, (16) until then; when the adapter does not take that command block (ILLEGAL REQUEST with ASC 0x20 or 0x24 and no drive registers, or a full read of zeros with a good status or a check condition that reports nothing wrong; "no drive registers" counts only when the sense data's descriptor list was read in full) the other form is sent once, and it is remembered only when the drive's data or registers come back. One reading of each reply (`sat::read`) decides both the answer and whether the other form is worth sending, so a short transfer stays malformed and the read limit is never sent twice after a status that may mean the drive took it. Every command is 28-bit, so both forms carry all its registers. The buffer holds the sense buffer and the sector after the header at 8-byte-aligned offsets; the reads use PIO data-in with the length in the count field, and the SCT command PIO data-out with CK_COND, its registers read from the ATA Status Return descriptor of descriptor-format sense data, or the fixed-format fields an adapter with D_SENSE off returns. A SCSI status other than good or check condition, sense data that says the command was not done (an adapter without SAT answers ILLEGAL REQUEST), a short transfer, or a read that came back as zeros is a failure naming what the adapter said, never an empty result; an error in the drive's returned registers is the drive's refusal. A source test keeps the controls to `execute` and the commands to the four `ata::Command` builds.

Fill the gaps (`recovery::fill::fill_gaps`) works on an image and map a finished or stopped rescue left, from a button in the rescue image window when the map shows areas not read yet (the folder's image and map are picked up when the folder is chosen). Each pass reads every sector not rescued once, one sector at a time, alternating direction (pass 1 forwards); 1 to 5 passes (3 by default) with a rest between them with nothing read (2 minutes by default); the drive's 10 s read limit; and a health reading after each pass, logged in the health log. When reallocated or pending sectors, or an NVMe drive's media errors, have risen by more than `rise_limit` (16) since the step began, it stops and says the drive is getting worse faster than it gives data back. A drive with no counts gets a warning and the passes still stop at their number or on Stop. A sector that reads goes into the image and the map at once, and the map is saved within a second of it (image flushed first); one that fails is marked bad. The map's phase and position are left as the rescue left them, so a later Resume and ddrescue read the map the same. The result gives each pass's recovered bytes.

## A drive that stops answering, the heat pause and the error pause

On 2026-11-09 a Seagate ST2000LM007 in a Seagate Expansion enclosure (UAS, no SCT error recovery control) was reset by its USB adapter inside bad areas three times, near 96.4 GB, 140.0 GB and 197.6 GB, the last at 30 C (Windows logged disk 153 and UASPStor 129). After each reset every read, size query and SMART query failed with error 1117 while Windows kept the device, so the disk still answered to its number; only a replug brought the drive back, as disk 3. The rescue took the 1117s for bad sectors, about 43 GB marked failed after the first reset and about 15 GB in 90 s after the third, until Stop, and the health log stopped for good after one failed query. The rule since: a read failure is recorded as bad or failed only while the drive is shown to answer; when it is not, nothing more is marked and the run pauses for the drive.

Detection (`recovery::disk`). A read on a physical disk that fails with a device error, or runs past its 20 s limit, asks `PhysicalDisk::answering`: the disk is still held (`HeldDisk::still_held`) and, for a volume, still present, and the drive answers IOCTL_DISK_GET_LENGTH_INFO within `PROBE_LIMIT` (10 s) with the same nonzero length as at the start. That query is read-only and reaches the drive each time (the disk class driver sends READ CAPACITY for it, where IOCTL_DISK_GET_DRIVE_GEOMETRY_EX is answered from a cache for a fixed disk); it goes through a handle of its own reopened from the held disk, and one that does not come back is canceled and its buffer left to the call. Ten seconds is half the read limit, so the probe never waits longer than the read that prompted it, and a probe given up on costs a pause, never a mark. A drive not shown answering gives `ReadError::Gone`. A runaway guard catches what the probe does not (`image::Streak`): after `RUNAWAY_READS` (64) failed reads in a row, or failures across `RUNAWAY_SPAN` (1 GiB), with no read coming back between, the source is asked (`BlockSource::answering`) before anything more is marked, and one that does not answer ends the pass as gone. 64 bounds what is recorded before asking to 4 MiB in the copying passes and 32 KiB sector by sector, and costs one size query per 64 failed sectors when scraping a real bad area; 1 GiB is far wider than a plausible bad area and is crossed within six reads by pass 1's growing skip on a 2 TB drive.

Pause and wait (`recovery::wait`). The read in flight is not recorded, and earlier marks are left as they are. The run moves past the place by the drop skip (`image::DropSkip`): 1 GiB, doubled for each further drop within twice the last skip of the last one, up to 5 % of the drive, in the direction the pass reads (copying and retries through the map's position, trimming and scraping through a floor they wrap from, Fill the gaps through its own position); the span skipped stays untried for the passes after, which come at it from the other side. A drive with no read limit of its own walks straight back into the zone it hung in, and on 2026-11-09 one zone ran from 137.4 GB to past 140.0 GB: 1 GiB clears a zone of up to 1 GiB on the first drop and, doubled, up to 3 GiB on the second, where pass 1's own first skip (61 MB on a 2 TB drive) would take six replugs; 5 % is 100 GB on a 2 TB drive, reached after seven drops in one zone, five times pass 1's largest skip. A drop during photos first ends photos first for the run, and pass 1 carries on in disk order. The map is saved (image flushed first), the window says "The drive stopped answering at <time>. Unplug it, wait 30 seconds and plug it back in; the rescue continues when the same drive is back." with Stop still there, and the health log says so. Every `LOOK_EVERY` (3 s) `wait::Disks` looks through disk numbers 0 to 31, none assumed: a disk of the drive's size and sector size is opened as a source is (`timed::open_source_within`, which proves the handle on the held disk and reads the drive's identity), and `wait::returned` judges it by the map's rule (`image::match_drive`: the drive's own serial number where both have it, else the serial Windows reports, and the size) and the sector size. A disk whose open did not answer in time is not opened again while Windows still holds it. Only the same drive is taken on its own: the run carries on with it from the same pass and place, the read limit is sent to it again (`ReadLimit::reconnect`, since a replug resets it), the health readings follow it to its new number (`HealthWatch::moved_to`), and the window says when it came back and as which disk. A drive that cannot be told from it (no serial number on one side) ends the run unread, with the map saved, and Resume asks the technician to confirm it (`Outcome::Unconfirmed`); another drive is never read. Stop ends the wait within a tenth of a second. A drive that stops again `STALLS` (3) times in a row with nothing read between is no longer waited for. An image file or an unlocked volume is not waited for: the run ends with the map saved, as before. Fill the gaps pauses and carries on the same way within its passes.

Health log (`recovery::health_log`). A failed health query is logged once per streak, the drive is still asked at every reading, and the next line comes when it answers, so the heat pause and the error pause work again once the drive does. A drive no longer listed by Windows at a reading is taken as gone, not paused for. When the read limit is not set (no SCT error recovery control, or an adapter that does not pass it), the window and the health log say that a bad area can then stall the drive long enough for Windows or its USB adapter to reset it, and that the rescue then pauses until it is plugged back in.

The heat pause (`timed::Throttle`) pauses work at a maximum temperature and resumes at a lower one. Rescue image and Fill the gaps have it, on by default at 38 C and 30 C, both set in the window before Start (the carry-on value is always below the pause value, and the engine refuses one that is not). While it is on, the temperature is read every 30 s with one health reading (SMART READ DATA on an ATA drive), from any source that reports one: SMART attribute 194, the NVMe health log or what Windows reports. At the pause value the run stops reading, saves the map, keeps reading the temperature every 30 s, and carries on by itself from the same pass and place at the carry-on value or below. The window shows the temperature, when it was read and both values, with Resume now and Stop; after 20 minutes without cooling it says a drive spinning in a warm enclosure may never get there, which is what Resume now is for. Resume now carries on at once, and the heat pause comes back only after the drive has been below the pause value. A run whose temperature cannot be read says the heat pause is not working for it. Each pause and carry-on is a line in the health log. The pause at the drive's own critical temperature stays.

The error pause (`image::WearRate`) judges how fast reallocated plus pending sectors (an NVMe drive's media errors) grow over a sliding window, not any single rise: on a badly damaged drive every bad area raises them a little, and the earlier rule, any rise of the reallocated, pending or uncorrectable counts since the first reading, paused the 2026-11-09 run at 15:57 when the counts went from 8977 and 488 at 14:54 to 9305 and 512. It pauses when they grew by the limit or more within the window, or, once the readings reach back over two windows, by half the limit while growing at least four times as fast as in the window before. The defaults, 1000 in 30 minutes, set in the window ("Error pause", 250 to 5000, or off), let that run go on: 312 in the 28 minutes to 15:57, under half the limit, 248 in the 5 minutes after it carried on at 16:06, and the 16 more reallocated sectors, pending unchanged, that paused it at 16:40 while it read cleanly at about 48 MB/s. A rise after a quiet window is not taken as speeding up unless it reaches half the limit. A drive in collapse still trips it: once most reads fail each one finds new pending sectors, and at one a second that is well over 1000 in 30 minutes; at the 50 a minute seen between 16:06 and 16:11 it pauses after about 20 minutes. The message names the counts, the window and the growth. The reading that pauses the run is logged once, at the run's position at that moment. Before, each pause was logged twice (16:11:53 and 16:11:57, 16:40:01 and 16:40:03, about 13 MB of position apart each time): the pausing reading went in at the position last published, up to 200 ms of reading earlier, and the rescue then took an end reading of its own, 2 to 4 s over USB, at the map's position. Reading already stopped at the pause decision; the position is now published before each reading and no end reading follows a pause.

The event log (`recovery::events`) lets a program watching a run read its state without polling the map and the health log. Rescue image and Fill the gaps add to `<image name>.events.jsonl` beside the image and map, one JSON object per line, never rewriting a line. Each line has the local time, the event, the run's state after it (running, paused, stopped, finished or failed) and the map's position and rescued, non-trimmed, non-scraped and bad bytes. The events are started (app version, disk number, the model and serial number Windows reports and the drive's own, the settings with the heat pause, the error pause and quick give-up), phase (each pass once, not again when it carries on after a pause), progress (every 30 s while reading, rescued bytes per second), read error (position, length, Windows error code, none for a time-out), health (the same fields as its health log row, written exactly when the row is), paused (the reason in words, a kind of error-rate, critical-temperature, heat, drive-gone or user, and the values that tripped it), resumed, drive gone (what showed it, with the read's error code), drive back (the disk number and serial numbers), stopped, finished and app error. Each change of state writes one event; a drive that cannot be told from the one being read ends the run paused with kind user, for the technician to confirm on Resume. The window's waiting, heat pause and end messages are the reasons of these events, so the window and the file say the same. A line is made whole in memory, written with one write and flushed; a line a killed process left part written is cut off when the next run opens the file. A heat pause before the image is open, while the first reading waits for the drive to cool, is shown in the window but not in the file, which does not exist yet.

## Opening an image, BitLocker and repair on a copy

Open an image as a drive (`recovery::vdisk::attach_image`, `gui/vdisk_view.rs`) attaches a raw rescue image read-only through the Virtual Disk API, so Windows gives its volumes drive letters and Explorer can browse them. Windows attaches only virtual disk files, so while it is attached the image carries a 512-byte fixed-VHD footer that only this tool writes (creator "dtol"); detaching cuts the file back to its exact length, and a footer left by a crash is removed on the next open or when a rescue resumes into the image. Every reader of an image file reads it without such a footer (`vdisk::data_len`) and never past the drive's size, so the footer is never taken for the drive's data, and the image's ddrescue map still applies. While attached, the image is held open with read sharing only, and the attachment ends with the process. A sparse or compressed image is stored plain first only when the options confirm it.

BitLocker (`recovery::bitlocker::scan`, `unlock_held`, `Relock`, `gui/bitlocker_view.rs`) finds BitLocker volumes on a drive or an attached image by their boot sector's "-FVE-FS-" signature, reads their lock state and recovery key IDs without unlocking, and unlocks one through Win32_EncryptableVolume with the 48-digit recovery key held in the zeroing `KeyText`. A volume on the drive being recovered is refused unless the options confirm it, after the advice to image the drive first and unlock the image instead. The unlocked volume reaches the recovery tools as `SourceChoice::Volume`, read decrypted, its disk taken from its own extents. The unlock reads the lock state first: a volume already unlocked is left unlocked, the key is not used and no relock is made; a state that cannot be read is refused. A volume this program unlocked from locked carries a `bitlocker::Relock` holding its identity (device ID, extents, key IDs). Lock, closing the window, and an unlock no window took in all lock through it, and it locks only while the volume is still unlocked and still the same volume. Every outcome other than locked is said; a forced dismount is asked for in the window and never done from a drop.

The key's copies: the typed text, the parsed key and the BSTR handed to WMI's `Put` are zeroed by this program on every path (`key_input`). `Put` copies the key into WMI's in-parameters object and the call marshals it to the WMI service and on to BitLocker; those copies belong to WMI and Windows and cannot be zeroed from here. That is a stated residual. What the program does about the one in its own process: as soon as the call returns it overwrites the key in the object with as many zeros and releases the object (`release_key_input`). Measured with a made-up key and no unlock (`bitlocker::tests::live_wmi_key_copies`, administrator, 2026-11-06), this process held the key's UTF-16 text in 6 places and its ASCII text in 1 once WMI had it; after the overwrite and release, 1 to 3 UTF-16 copies in memory WMI freed or keeps (3 in each of two runs on 2026-11-07); released without the overwrite, 5 or 6 and the ASCII one. The copies in the WMI service and BitLocker were not measured. No unlock path left to this process takes the key in buffers it owns from end to end: Win32_EncryptableVolume is the documented interface, manage-bde would take the key on a command line, and the FVE API's unlock exports are undocumented. The copies in memory WMI freed or keeps therefore stay a stated residual, and the dump rules below keep them out of dump files.

Crash dumps and the key. While this program holds a recovery key, a dump of its memory holds the key. Measured on Windows 11 (a Windows 11 test machine, 2026-11-06, a test program holding marker text): with LocalDumps `DumpType` 2 its full dump held text on the heap, text in a block registered with `WerRegisterExcludedMemoryBlock` and text on the stack; `WerSetFlags(WER_FAULT_REPORTING_FLAG_NOHEAP)` and `ExcludedApplications` did not change that; a fail fast (the way a Rust abort ends) was dumped too; a program's own LocalDumps key with `DumpType` 1 still held the heap text, and with `DumpType` 0 and no flags the stack text; with its own `DumpCount` 0 no dump was written, for an access violation and for a fail fast. So: A LocalDumps key holding only another program's own key, with no value of its own, as drivers and utilities leave it, turned dumps on for every program: a test program with no key of its own was dumped (2026-11-06). In a later run with LocalDumps `DumpType` 2, a program kept out by its own `DumpCount` 0 left no dump, and without it its full dump (82 MB) held the key's text once in a block registered with `WerRegisterExcludedMemoryBlock` and once in an unregistered one. So: before a recovery key enters the process (the BitLocker window opening, an unlock, a key file search, the account sign-in), `crash_dumps::keep_out_of_dumps` writes this program's own `LocalDumps\<its file name as it runs>` `DumpCount` 0 whenever LocalDumps exists and the value is not 0 already, reads it back, and adds it to the session's change record (the elevated recovery copy is given the record's path, as the crash dump copy is). `%ProgramData%\DiagnosticTool\recovery-dump-exclusion.json` lists each process relying on it (its id and start time) and what was written, saved before the write. The last process to let go (the BitLocker window closing after it locks its volumes again, or the unlock or search that took a key ending) puts the value back as it was and removes the key it made when empty; a file whose processes all ended is settled the same way when the recovery window next starts. Every value holding a key (`KeyText`, `RecoveryKey`, `SecretKey`, so each key in a search or sign-in result, also after the lookup returned) and every key file search thread, which can run past the time limit, holds a reference-counted share of the exclusion; the last share dropped in the process lets it go. Letting go takes the value away only while it is still the 0 this program wrote; a value changed since is left as it is, and the change record says so. The BitLocker window keeps its key box, Unlock and Find the key off until the exclusion is held, clears a key already in the box when it is not, says why, and tries again on each choice in the window. A key is refused only when the value cannot be written or does not read back 0, with the reason and what to do (run with administrator rights, or turn application dumps off), or when AeDebug starts a debugger by itself on a crash. Crash dump set up gives this program the same exclusion whenever LocalDumps is on after it, written before any other value, saved and taken away by Put back like the rest. The two hand it over rather than remove it while the other relies on it: Put back leaves the value, and the keys set up made for it, to a running recovery window and names them in the file, and a recovery window letting go while set up's saved settings exist adds its value and keys to those settings for Put back. One lock (a named mutex) covers the exclusion, set up and Put back. Each buffer that holds a key (`KeyText`, `SecretKey`, `RecoveryKey`, the page and key file text, the key file's bytes) is also registered with `WerRegisterExcludedMemoryBlock` while it lives (512 blocks a process at most, measured), which the measurement above shows LocalDumps ignores; it stays as a request for report dumps. Set up refuses full application dumps while this program holds, or has held since it started, a key (a named mark, `bitlocker::mark_key_held`, kept until the process ends, since freed memory can keep a key's text). Residuals: when the exclusion is refused, a key already typed into the window's box is in the window's memory until the unlock clears the box; two copies of this program with different file names cannot hold the exclusion at once, and the second refuses; a debugger set to start by itself on a crash is refused rather than excluded (AeDebug's `AutoExclusionList` could exclude this program, not built or measured); a complete or active kernel memory dump holds every process's memory, this one's included, and is the technician's choice in Crash dump readiness; Windows Error Reporting may still queue a report of a crash, which with consent can carry a small dump to Microsoft; a debugger attached by hand, or a dump taken by hand from Task Manager, is outside any setting.

The window can find the key instead of having it typed (`recovery::keylookup`). First `search_key_files` looks for "BitLocker Recovery Key <ID>.TXT" files for the volume's key IDs on every mounted fixed and removable drive (the root and two folder levels, never network drives), each drive on its own thread with a time limit, and checks each file's key as a recovery key and its stated ID against its name. If none is found, the window offers the sign-in window (`gui/keylookup_view.rs`, `keylookup_view::fetch_recovery_key`): the customer signs in on Microsoft's own pages in a WebView2 window limited to Microsoft's sign-in and account hosts over HTTPS, and the key for the volume's key ID is read from the visible text of the account's recovery key page. The WebView2 runtime already on the PC is loaded by its full path after its Microsoft signature is checked; its data folder (the signed-in session) is a new folder under %TEMP%, removed when the window closes. A key found goes from the lookup's zeroing `SecretKey` straight into the unlock's `KeyText` and is dropped; the window says only where it came from. Without a key, the technician types it.

Repair on a copy (`recovery::repair`) never repairs the source drive or its image. It makes a VHD differencing disk over the attached image, attaches the copy read-write, and writes only to it: a partition table rebuilt from the lost-volume search, or `chkdsk /f` on one of its volumes. The one writable disk handle is `handles::CopyDisk`, opened from the disk number Windows gave this run's copy; it refuses the source disk and the system disk, and is checked through its own handle to be backed by the copy's file before each write. A volume Windows mounted from what is left of the old table (a backup GPT, for example) is locked and dismounted through the copy's handle before the new table is written and held closed until Windows has read it; written under a mounted volume, the table left that volume open on the old layout and chkdsk could not open the new one (exit 3, "Cannot open volume for direct access."). `chkdsk` runs on a volume's GUID path only after the held copy shows that volume lies on it, and an exit other than 0 to 2 is said with chkdsk's own last line. The copy is attached without drive letters, for every volume it shows, so Windows Search does not take it up and write its catalog id to it while it is being repaired (measured: a lettered volume gets `System Volume Information\IndexerVolumeGuid` within 30 s, one without a letter does not); its volumes are browsed after the repair by opening the kept copy, read-only, with Open an image as a drive. Before the copy is detached, each of its volumes is locked, written out and dismounted through the copy's handle, and held closed through the detach: the closed volumes travel with the detach job and are let go only once Windows has answered it, also when that is after the detach's time limit. Windows mounts a volume again after chkdsk, and a detach under the mounted volume cut off its last writes (measured: paging-operation errors at the detach, and the kept copy's NTFS volume then did not mount) or waited 180 s for them. The volumes closed are the whole set Windows places on the copy (`target::every_volume_on`, as a replacement drive's are), read within 30 s since a failing drive's volume can stop answering (`timed::in_time`; the H guard covers this read as it does the changes it gates): a list not read in time or cut short, or a volume Windows does not place, stops the detach, and the table write, as a volume that does not close does. So a volume that does not close stops the end: the copy is not detached and stays attached, the window says why and the repair can be ended again; a window closed without a choice keeps such a copy attached until the process ends, and says so in the change record. A kept copy is entered whole only once its detach has succeeded; a failed or late detach leaves it partial, and its record and the window say why. The replacement drive likewise is whole only once it confirmed the last writes as the writer let it go, and its window says Finished only then: the headline and the ledger read the same condition (`restore::drive_condition`). The copy is kept as the repaired copy or discarded.

## Copy the customer's files

Copy the customer's files (`recovery::migrate`, `gui/migrate_view.rs`) reads an old Windows drive or a rescue image through the app's own NTFS reader, so the drive is only read and failed reads follow the rescue copy's rules. It finds each Windows installation, then copies each person's own folders, OneDrive files that are on the drive, browser profiles without their caches, Outlook data files and Sticky Notes to another drive, and writes a report a technician can hand over with the Windows product key, decoded from the offline SOFTWARE hive by a bounds-checked reader, and the saved Wi-Fi networks' names and security types. Saved passwords are not extracted: a browser profile's saved logins are encrypted to the old Windows account and do not carry over, and the report says so; Wi-Fi passwords are not decrypted.

## Check recovered files

Check recovered files (`recovery::verify::run`, `gui/verify_view.rs`) walks a folder of recovered or copied files and sorts every file into good, damaged or not checked, with a one-line reason, by its contents, never by its name alone. Each format's structure is walked from start to end with every length kept in bounds, and checksums are checked where the format has them (ZIP entries and PDF streams are decompressed with `flate2` and their CRC-32s tested); pictures are not decoded. Every byte read is treated as hostile: no allocation is sized by a field in the file, and each file's check runs within `verify::LIMITS` (its time and the bytes it may unpack, stored ZIP entries read for their checksums included, set by the options; 16,777,216 parts; 512 MiB held; boxes 16 deep); a limit reached makes the file not checked, saying which. The folder is listed within `verify::LISTING` (4,000,000 entries, folders 255 deep), and an entry the listing could not give is a row of its own. Files are read through ordinary shared handles and never written; the one thing written is the report, through `dest::Guard` into the folder checked. Rescue copy of files, Recover deleted or lost files and Find files by type offer it on their output folder.

## Write image to a replacement drive

Write image to a replacement drive (`recovery::restore`, `recovery::target`, `gui/restore_view.rs`) is the one recovery tool that destroys data, on the drive it writes. The image and its map are held open with read sharing only. A disk is refused, through handles and device numbers, when it holds the image or map, the Windows folder, the system partition, the running program or a page file, when one of its volumes spans another disk, when it is smaller than the image or its sector size does not match a GPT image's, and when it is the drive the map names (the same serial number, or, when either has none, the same model and size); a guard that cannot be found refuses every disk. The tool is an engine with no window in it: `target::candidates(image)` lists every disk with its refusals and the confirmation it needs, and `target::write_image(&WriteOptions, events, cancel)` writes and returns a `WriteResult`; the options (image, disk number, confirmation, grow), the progress `Event`s and the result are serde types, and the window only builds the options, shows the events and renders the result. The confirmation is a field of the options, chosen so no other connected disk shares it: the serial number's last four characters; when another disk's serial ends the same way or there is none, the first eight characters of the disk ID (the GPT disk GUID or the MBR signature); failing that the size and location (port:bus:target:LUN); and only when Windows gives neither, the disk number and size. Disks are read through handles with no access right (identity, size, sector size, disk ID and location). Just before writing, the engine opens the disk, keeps that handle, reads the disk through it and checks every refusal and the confirmation against it and against every connected disk (`target::clear`); only a `Cleared` opens a disk or its volume for writing. A handle stays with its device, so every open for writing ends by checking that the held handle still answers to the disk's number: a drive disconnected, or another taking its number, is refused. The disk handle opened for writing is checked by device number, identity, size, disk ID and location before any of its volumes is listed or touched. The volumes closed are the whole set on the disk: a volume whose disks cannot be read, unless its own device number puts it on another device, stops the write. Volumes are locked and dismounted and the disk is taken offline (not persistently) while it is written, unbuffered and write-through. Offline and online are compare-and-swap: the disk's attributes are read first, it is taken offline only if it is online, and brought back online only if this run took it offline and it is still offline. A disk whose sector size Windows does not report is refused, never taken as 512 bytes. The first MiB and the drive's last MiB are zeroed first, everything after the first MiB is written in order with areas not rescued as zeros, and the first MiB last, so a stopped or failed write leaves no partition table. Each 4 MiB chunk is hashed as written and read back after. Growing the last partition is off by default: GPT moves its backup entries and header to the new end, MBR extends the entry, a recovery partition or a logical drive last is left alone, and NTFS is extended by Windows with FSCTL_EXTEND_VOLUME. `Write report.txt` goes beside the image.
## Crash dumps

`tools::crash_dumps` has three entry points, `check`, `set_up` and `put_back`. Each takes a serde options struct whose fields state their bounds, a progress callback with typed events (`Step`, `Item`, `Changed`) and a cancel flag, and returns a serde result, so the window and a later agent interface drive the same engine. Every rule lives in the engine; the window builds options, shows events and renders results. All reading and writing goes through the `Machine` trait (registry in the 64-bit view, volumes, folders, files, the saved-values file and the change record); the tests run the engine against an in-memory machine.

| Rule | Source |
|---|---|
| `CrashDumpEnabled` 0 none, 1 complete (active with `FilterPages` 1), 2 kernel, 3 small, 7 automatic; changes take effect at the next restart | Microsoft, Memory dump file options |
| a page file on the Windows volume or a dedicated dump file must hold the dump: small 2 MB, complete and active RAM plus 257 MB, kernel and automatic the kernel memory in use now plus 257 MB; a system-managed page file may grow to within 1 GB of the volume's free space | Microsoft, How to determine the appropriate page file size for 64-bit versions of Windows |
| MEMORY.DMP is deleted after a stop when its drive has under 25 GB free, unless `AlwaysKeepMemoryDump` is 1 | Microsoft WER team, Kernel dump storage and clean up behavior in Windows 7 |
| `LocalDumps` `DumpFolder`, `DumpType` (1 mini, 2 full), `DumpCount`; local dumps are written even with reporting turned off, and not when AeDebug starts a debugger by itself | Microsoft, Collecting User-Mode Dumps |

Set up refuses a confirmation it was not given, a process without administrator rights, a path that is not a plain path on a drive letter, a network, removable, CD or RAM drive, a link or file where a folder belongs, a variable other than `%SystemRoot%` in kernel paths or a per-account one in the application folder, a dump type the page file cannot hold (naming the size needed) and a drive without room. Unconfirmed, it returns the changes it would make. It writes only what differs (a path naming the same place is left), saves each value's type and bytes to `%ProgramData%\DiagnosticTool\crash-dump-settings-before.json` and reads the file back before the first write, keeps the first saved value when it runs again, and reads every value back after writing. The application dump folder it makes has a protected access list: SYSTEM and Administrators full control, CREATOR OWNER full control of files, and signed-in accounts may list and add files, so each dump is readable only by its own account, administrators and SYSTEM. A link anywhere in a dump folder's path is refused, from the folder up to its drive, the deepest folder that exists must resolve to itself, and each folder set up makes is checked through its own handle before a setting names it; the check reports a dump folder under a link the same way. A dedicated dump file or fixed page file counts as room for a dump only when its drive can hold the file at its set size. Put back first checks the saved file against exactly what set up writes and makes, and refuses it, changing nothing, when it names any other key or value, a value twice, a value larger than a setting, a key other than LocalDumps and this program's own LocalDumps key, a folder that is not a plain path below a drive, or a format it does not know, or a value recorded as written that set up never writes; a file from an older version is refused with the values it holds, to put back by hand. It restores each saved value byte for byte, or deletes it if it was absent, only while it still holds what set up wrote: a value changed since is left as it is and said, and set up run again takes a value changed since its last run as the one to put back. It removes the keys set up made only when empty and still the keys it made (their last-write times, recorded after each write), removes a folder set up made only when empty and still the very folder it made (its volume and file ID, recorded once made), keeping any other with a note, and removes the saved file once every value reads back as saved. While a recovery window relies on this program's own exclusion from application dumps, Put back leaves that value and the keys made for it to the window, which takes them away when it lets go; an exclusion left by a window that ended is settled first. Listing the dumps already there looks at no more than 20,000 entries in each place and stops with the check; closing the window does not wait for a check that Windows holds up in a folder read.

The main window starts an empty change record in the temporary folder; the elevated copies (crash dumps and recovery) are given its path and add each set up, put back and exclusion from crash dumps to it. The report's Changes made lists the record, and a record that grows after the report was saved saves a new report.

## Undoing a change

Every restore is compare-and-swap through `crate::restore::put_back_if_still`: a place is put back to what it held before only while it still holds exactly what this program wrote, read back after. A place changed since is left as it is and said; one that cannot be read is left and said. Crash dump Put back and the exclusion's settle restore registry values that way; a key this program made is removed only while its last-write time is the one this program left it at (`crash_dumps::places::Custody`), and a folder only while it is the folder set up made and empty. The BitLocker relock and the update's rollback (by file identity, renamed through the handle) use the same function. A source guard (`restore::tests::every_restore_writes_only_through_compare_and_swap`) keeps it the only way a restore writes.

A place has no plain write: it writes only through `Place::swap`, which compares and writes as one operation wherever Windows offers one. A registry value is put back in a kernel transaction: the transaction writes the value, the committed value is read outside it and compared, and the transaction commits only when it matched. Measured on the test machine (`crash_dumps::windows::tests::live_registry_transaction_against_another_writer`): a writer outside the transaction is not held back, but its write aborts the transaction, so the commit fails and its value stays; a write to another value of the same key aborts it too, and the value is then left and said. A key this program made is removed the same way, compared by its last-write time and found empty. A folder is checked by its identity and removed through one handle, and the file system refuses to remove a folder that holds anything; the moved-aside program is checked and renamed through one handle. Where Windows offers no such operation, the place checks again just before it writes and its residual is in a `Residual:` comment beside the code: a BitLocker volume's lock (its state read and the lock sent on one WMI connection, one call apart; a volume locked and unlocked again by someone in that moment would be locked again), the drive's read limit (the read and the set back to back on the held drive; another program setting the limit in that moment would be overwritten) and the replacement drive's offline attribute (read and set back to back on its held handle; a disk another program took offline in that moment would be brought online). A source guard (`restore::tests::every_place_compares_and_writes_as_one_operation`) checks every place.

## Processor and memory

`tools::cpu_memory` holds two engines with no window in them, so the window, the report and a later agent interface drive the same code.

`details(&DetailsOptions) -> Details` reads once, as the current user. The processor comes from CPUID (vendor, brand, signature, instruction sets, and the cache leaf 4 on Intel or 8000001Dh on AMD), GetLogicalProcessorInformationEx (packages, cores and their efficiency classes, so a hybrid processor's performance and efficient cores are counted, caches with size, ways and sharing, NUMA nodes) and CallNtPowerInformation (each processor's base, current and allowed clock; Windows' current figure often stops at the base clock, and the window says so). Memory and board come from the firmware's SMBIOS table through GetSystemFirmwareTable('RSMB'): BIOS (type 0), baseboard (2), sockets (4), memory arrays (16), devices (17) and mapped ranges (19), with offsets and codes from DMTF DSP0134. A table whose header gives more bytes than Windows returned is read only as far as it goes, and the window, the copy and the report say it was cut short. The table is firmware's and may be malformed, so every read is bounded: a field is read only inside its structure, a structure only inside the table, strings are cut at 128 characters and the walk stops at 4,096 structures; the tests cut and corrupt a table byte by byte and feed random noise. Channels are given only when every filled slot's names say "channel" and a letter or number. A design name is given only from a cited table: Intel codenames from the Linux kernel's `intel-family.h`, leaving out models it says several codenames share, and AMD Zen generations from its `amd.c`. Serial numbers are read only when the options ask (the window does); the report's rows never carry them. Detailed memory timings need SMBus access through a kernel driver and are not read.

`monitor::run(&MonitorOptions, on_event, cancel) -> Summary` samples at an interval of 250 ms to 10 s (1 s by default) until canceled or a sample count is reached, sending `Event::Started` with the fixed figures and then one `Sample` per interval: plain data with units in the field names (percent, MHz, bytes, seconds, milliseconds since 1970), so it can travel as JSON to the technician's live monitor later. Processor use and the clock come from PDH's Processor Information counters (% Processor Time per logical processor, % Processor Performance against Processor Frequency), memory, commit, pools and the process, thread and handle counts from GlobalMemoryStatusEx and GetPerformanceInfo, and the modified, standby and free page lists from PDH's Memory counters; in use is the total less those lists. A processor whose counter gives no valid value keeps its place as none, so processor N is always at index N. The summary gives each series' minimum, average and maximum. The window keeps the last 1,800 samples (30 minutes) in a `History` ring that never grows past that.

## Session

A session is one consented run with a five-minute lifetime. Checks run one at a time in registry order. Each ends as found (with a short brief and a flag), unavailable (with a reason) or stopped. Pause cancels the running check and returns it to the queue; Resume runs it again. Stop, closing the window, or expiry cancels the running check and marks every unstarted check as not run. When the session ends the report is written on a worker thread; the window stays until it exists. A second launch brings the running window forward.

## Runner

Windows version, Hardware inventory, Restart and crash settings, Update history, CPU and memory and Drive health status are fixed PowerShell scripts with no interpolated input; the other checks read in-process (see Event log engine). PowerShell is started by its absolute System32 path with `-NoProfile -NonInteractive`, no window, below-normal priority and suspended, assigned to a job object that kills the whole process tree when closed, then resumed. Output is read up to 4 KiB and time is limited to 12 seconds; a canceled, timed-out or flooding check ends its job. Scripts emit small ASCII `key=value` fields that strict parsers turn into outcomes; anything unexpected becomes unavailable with a reason.

## Report

The PDF is built as a list of plain blocks (heading, paragraph, row, bullet) and then laid out on A4 pages with embedded Noto Sans, so its content is tested without parsing a PDF. Page one gives the date, version, an at-a-glance summary that puts flagged results first, then checks that could not run and why, the full checks table, what the results cannot tell, changes made and next steps. Later pages hold the hardware inventory and per-check detail with the session record. An unavailable or not-run check is never shown as passed. The file goes to the user's Documents Known Folder (including OneDrive redirection) as `Diagnostic-Tool-<local date and time>-<n>.pdf`, created new so no earlier report is overwritten; if saving fails the window offers Save report as.

The inventory reads CIM classes for system, board, processor, memory modules, drives, graphics and firmware. It excludes serial numbers, service tags, MAC and IP addresses, user names and product keys. Placeholder board revisions and zero-capacity removable drives are shown as not reported or unavailable, not as facts.

## Interface

The visual language is a zinc palette on a near-black page, rounded cards, one light primary button, restrained green, amber and red for results, Segoe UI Variable in three sizes. Controls are owner-drawn statics and buttons whose window text is their accessible name, so screen readers read each row as "label: result". Shapes are drawn anti-aliased with GDI+ and text with ClearType. Layout is recomputed from `ui_layout` when the window's DPI changes. In high-contrast mode the palette switches to system colors. Focus rings appear once the keyboard is used. Tab and Enter work in every window, and Escape declines a dialog.

Rows whose check has a tool are owner-drawn buttons drawn as rows, with a chevron, a hover highlight and a hand pointer; clicking or Enter opens the tool beside the main window, and opening it again brings it forward. A tool window is resizable, uses the same palette and controls, and closes with the main window. Its lists are owner-drawn list boxes, so they scroll and take the keyboard natively and screen readers read each item's text. Each list item is painted into its own bitmap from 0,0, because GDI+ ignores a viewport offset for GDI text drawn while it holds the device context.

The drive space window maps the whole Windows drive with eight threads sharing one folder queue (811,070 folders in 19 s on a development workstation), keeping each folder's total and its 50 largest files, so any folder can be opened without a second walk. Junctions and links are not followed and cloud-only files count as nothing; folders the user cannot read are counted and named in the status line. Clean up runs as the current user. A temporary file is offered only when it sits in the user's or Windows' temp folder, reached without following a junction or link, is not itself a link, read-only or a system file, and was created and last changed more than 7 days ago; each is checked again just before removal, files in use fail and are left, and a folder is removed only when empty and created more than 7 days ago. The temp folders themselves stay. The Recycle Bin is emptied for every drive through the shell without Windows' own prompt, after the window's confirmation names both parts, their sizes and that they cannot be brought back.

A panic or a native fault writes `Diagnostic-Tool-crash-<time>.txt` beside the reports and tells the user where it is; a fault note names the module and offset and carries a backtrace.

## Event log engine

`src/events.rs` reads event logs in-process with `EvtQuery`, newest first, filtered by an XPath built only from checked names, numbers and a bounded time range, and renders each event's source, id, level and time through the system render context. The reading thread runs in background mode, so its CPU and I/O priority drop; it checks Stop between batches of 64 and ends at the check's deadline or a per-log event limit, and the result says which limit was reached and how many events could not be read. Events are grouped by log, source and event id with counts, the most severe level, and first and last times. Kinds in the versioned noise table are counted and hidden. The rest are ranked: known serious kinds (unclean shutdowns, blue screens, WHEA hardware errors, drive, controller, file system and graphics driver failures) above known notable kinds (service, app and update failures, low memory, crash dump and Secure Boot failures, lost shadow copies, network port exhaustion), then unknown kinds by level; recency and count order kinds within a tier. The survey reads 7 days of critical, error and warning events from System and Application, up to 2,000 per log, and flags known serious kinds only. App crashes, Service failures and Hardware and driver events use the same engine with narrow queries of sources and ids (the hardware check one query per kind, each under 22 `and`/`or` operators), 7 days and up to 1,000 events per query. They also ask the engine for `EventData/Data` items by name, which carry the faulting app, module and exception code of event 1000 and the service of the Service Control Manager events and read the same in every language; names are redacted and cut. Crash dump readiness reads 30 days through the crashes tool's reader, and Drive wear and errors through the drives tool's reader. Each check says in its report detail the rule behind its flag. An excerpt formats one kind's newest message with its source's message table and removes computer and account names, profile folder names, account SIDs, e-mail, IP and hardware addresses before capping it at 400 characters. Each noise rule and known kind has a fixture test, and a GUI test measures every row text the in-process checks can produce against the row's width.

Clicking Recent system events, App crashes, Service failures or Hardware and driver events opens the event viewer for that row (`src/event_list.rs`, `src/gui/event_view.rs`). It reads the row check's own queries again on a background thread, with messages redacted as above and capped at 4,000 characters, within 30 seconds shared between the queries, and lists the events newest first with the check's own filtering (the survey's routine kinds stay hidden, the crash, service and hardware views keep only the kinds their check counts). Level, range and text filters apply in memory; a longer range or a level the check did not read reads again, with up to 5,000 events per log for 30 days. A log that cannot be read, or a limit that cut the range short, is said under the filters. The selected event's fields and message can be copied, and Search the web opens the default browser on a search for the source and event id only.

## Toolkit

`toolkit <tool>` runs one read-only tool from a console, so a repair does not depend on what the PC has installed. Every tool runs as the current user, reports anything that needs administrator rights as unavailable with that reason, finishes within a stated time, caps its lines and says when a limit cut it short. Free text from the PC passes through the event engine's redaction; serial numbers, hardware addresses, product keys and Wi-Fi network names are left out. Each tool returns its readings twice from one interpretation: short labeled lines for people, and with `--json` the same readings as snake_case fields for the AI model, with times as RFC 3339 UTC strings, sizes in bytes, an unavailable reading as an object holding its reason, and a limit that cut the output short stated in a field. Redaction applies to both forms.

| Tool | Reads |
|---|---|
| `events` | the event engine: ranked kinds by log, source, id, level and time range, and one kind's newest message |
| `timeline` | installs, updates, drivers, boots and failures merged by local day, with repeats and bursts folded, up to 365 days back |
| `crashes` | stop codes and drivers from event 1001 and crash dump headers, unclean restarts, and failed crash dump setup |
| `drives` | each disk's NVMe health log or SMART attributes, temperature, failure prediction and drive errors |
| `startup` | Run keys, Startup folders, scheduled tasks, services and drivers with their signers; lists flagged entries and counts the rest per section, with `--list` and `--all` for more |
| `network` | adapters, gateway and DNS reachability, proxy settings, the hosts file (names of well-known domains or on public addresses, the rest counted) and Wi-Fi signal |
| `perf` | a timed sample of processor, disk and memory use per executable |
| `battery` | design against full-charge capacity and cycle count |
| `space` | the largest folders on a drive, walked by eight threads within 60 s, and cleanup candidates |
| `hash` | one file's SHA-256 or SHA-1, size and times, and its Authenticode signature (embedded or catalog) with the signer and why it is not valid |
| `drivers` | third-party driver packages in the driver store (provider, class, version, date, signer) and present devices with a problem code and its meaning |

## Adding a check

Add a `CheckSpec` with a stable id and plain label to `CHECKS` in `src/checks.rs`, a fixed read-only script and a strict parser (in `src/expanded_probes.rs` for extended checks), and fixture tests for normal, malformed, unavailable and partial output. The GUI queue, the window rows and the PDF follow the registry. A check reports missing access as unavailable and never reads personal files, credentials or full event messages.

## Repairs

Repairs are what the survey leads to. This version ships the survey; the repair runner comes with the remote path. The technician and the AI model decide each repair; the user authorized the work by asking for help and choosing Start, and is not asked again. Before a runner carries a repair out, the repair declares a stable action id, typed arguments, scope, expected interruption, elevation, verification and rollback (`RepairPlan` in `src/lib.rs`; `undeclared()` names anything left blank). A repair that needs administrator rights goes through Windows' own administrator prompt; nothing else elevates. Every command and change goes in the activity record, and the session ends with Stop, Disconnect or expiry. A passing diagnostic never stands in for a repair's verification.

## Remote support

Remote support, when activated, lets the technician and the AI model they work with run cataloged diagnostics during a live session, and later the repairs they decide on. The executable opens the only connection, outbound to an authenticated relay; it never listens and stores no enrollment.

1. The user consents to one short session. The client connects out and shows a one-time code if matching needs it. No shared key or credential is compiled in.
2. The technician authenticates to the relay and matches the code. The relay binds the single-use pairing to the technician's identity and declared scope. The user's window shows the verified identity, discloses that an AI assistant may help read results, and keeps Disconnect available.
3. Each request carries session id, unique request id, command id, typed arguments, capability, deadline and output limit. The relay checks membership; the client checks consent, scope, replay and deadline again. Expired or duplicate requests fail closed.
4. Commands come from the same audited catalog, run one at a time through the runner, and are redacted on the client before upload and on the operator side before AI input.
5. A command outside the reviewed catalog is refused; the relay and the client each check the catalog. Repairs go through declared repair actions (above), and elevation only through Windows' own administrator prompt.
6. Both sides keep an activity record of the start, pairing, every command and change, cancellation, exit codes, redaction, expiry and disconnect, with capped and redacted results.

`src/support_transport.rs` holds the relay's HTTP handlers with RS256 operator JWT checks, single-use matching, one command at a time, 15-second pending deadlines, replay refusal and Disconnect revocation. `src/support_client.rs` holds the outbound HTTPS clients. `src/operator_tools.rs` exposes `session_status`, `command_catalog`, `request_command`, `cancel_command`, `activity_log` and `end_session` as MCP tools; only `request_command` causes local execution, and only in a live, consented session. `src/bin/support_relay.rs` and `src/bin/operator_mcp.rs` exit disabled in default builds. The GUI's remote worker starts only when built with the `live_support` feature and the activation marker; the relay endpoint comes from the build's site settings.

The catalog also holds one read-only command per toolkit tool, `toolkit.<name>`, built from the tool registry so a new tool appears without a catalog edit. Its typed arguments must be plain tokens (letters, digits and `._:-\`, at most 64 characters, at most 16 of them) and must fit the tool's usage: known flags, whole numbers within the stated range. The MCP adapter, the relay and the client each check them before accepting or running the request. The client runs the tool in-process, takes its JSON when it has one and its text otherwise, redacts and caps the result to the 4 KiB output limit, and records command, arguments, duration and outcome. Each toolkit command's deadline is its tool's own time bound plus 5 seconds, from a table in `src/protocol.rs` (events 65 s, timeline and startup 35 s, crashes and drives 25 s, battery 10 s, network 35 s or 15 s with `--quick`, perf and space their `--seconds` value plus 5 s); the hardware inventory has 35 s (its own 30 s bound, since loading the PnP module took 5.7 to 8.3 s on a 2014 Xeon VM), and the other fixed diagnostics keep 15 seconds. The deadline, Stop and Disconnect end the wait; the tools take no cancellation flag, so an abandoned tool finishes in the background within its own time limit, its result is dropped and no other tool starts until it does.

The user's executable holds no credential for any agent or messaging system, and the operator side is a separate component. There is no RDP, screen capture or screen-sharing component.

## Distribution

A release is one exe and its SHA-256, built reproducibly by `cargo xtask dist` ([docs/RELEASE.md](docs/RELEASE.md)). Publisher trust needs an Authenticode signature from a trusted certificate; a self-signed file does not establish it. Third-party notices ship with the binary.

Updates are optional and set at build time. The build's site settings give `update_base`, an https base address where signed release manifests live, and `update_public_key`, the public half of an ECDSA P-256 key as 128 hex characters; a build without both does not update itself. The private half stays off the build machine. Publishing builds the manifest (product, version, file name, size, SHA-256, publish time), signs it offline and uploads the program and `latest.json` (the manifest and its signature, both base64) under the base address. At start the window fetches `latest.json` over WinHTTP in the background, with Windows' proxy settings and certificate store, no redirects and a 16 KiB cap, and verifies the signature with ring before reading anything else from it. A newer version shows an Update button with a download arrow under Close, enabled once the report is saved. The program is downloaded (64 MiB cap) and must match the signed size and SHA-256; the running program is renamed aside, the new one moved into its place and started with `--after-update <pid>`, which waits for the old process to end and then deletes the renamed file. Any failure leaves the old program in place and says why. A failed check is silent.
